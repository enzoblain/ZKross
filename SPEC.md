# ZKross specification

Formats that the circuits, the Stellar pool (`spp/contracts/pool-gvk`) and the Ethereum pool (`contracts/ethereum/src/ShieldedPool.sol`) must agree on. Part A restates SPP's existing formats; Part B defines the bridge. Test vectors are in `contracts/ethereum/test/fixtures/spec_vectors.json`, generated by `scripts/poseidon2/spp-poseidon2-vectors` from SPP's own Poseidon2 code, and checked in Rust, Circom and Solidity.

SPP is pinned at commit `9bc3a78b90c84b144e86af04c9c331a684f528dd`. Links below go to that commit; base URL `https://github.com/NethermindEth/stellar-private-payments/blob/9bc3a78b90c84b144e86af04c9c331a684f528dd/`. Full detail on Part A is in `docs/spp-encoding-notes.md`.

Notation: `r` is the BN254 scalar field size. `P2(a, b; tag)` is SPP's 2-input Poseidon2 (`perm_t3(a, b, tag)[0]`) and `P3(a, b, c; tag)` its 3-input one (`perm_t4(a, b, c, tag)[0]`). Field elements travel as 32-byte big-endian integers below `r`.

## Part B: bridge formats

### B1. Units and decimal conversion

| Chain | Token | Note amounts are in | `scale` |
| --- | --- | --- | --- |
| Stellar testnet | Circle USDC via its Stellar Asset Contract | stroops, 10⁻⁷ USDC | 10 |
| Ethereum Sepolia | Circle USDC ERC-20 | 10⁻⁶ USDC | 1 |

- **Notes stay in each chain's own base unit.** SPP's `transact` moves tokens 1:1 with note value, so Stellar notes must stay in stroops.
- **A bridge message carries `amount` in 10⁻⁶ USDC ("bridge units").** This is the coarser of the two units, so every bridge amount exists on both chains.
- **Source side:** the spent value is `amount × scale_src`. Bridging from Stellar therefore always moves a multiple of 10 stroops. The leftover digit is never rounded: it stays in the sender's change notes, because the circuit enforces `in0 + in1 = out0 + out1 + amount × scale_src`. A wallet picks `amount = floor(value / scale_src)`.
- **Destination side:** the new notes hold `amount × scale_dst` in total. 10⁻⁶ → stroops is ×10, always exact.
- **`scale` is a public input set by the contract**, never by the user. Each circuit also checks `scale ∈ {1, 10}`.
- **`amount < 2^64`**, checked in-circuit. That is about 1.8 × 10¹³ USDC, far above supply, and it keeps `amount × 10` far below 2^248.

Examples: 1.2345678 USDC on Stellar is 12 345 678 stroops. It can bridge `amount = 1 234 567`; 8 stroops stay in change, and Ethereum receives 1 234 567 (1.234567 USDC). Bridging 1 234 567 back gives 12 345 670 stroops on Stellar.

### B2. Chain IDs and asset ID

| Name | Value | Why |
| --- | --- | --- |
| `chain_id(Ethereum)` | the EIP-155 chain ID (Sepolia: 11155111) | the standard EVM identifier |
| `chain_id(Stellar)` | `2^64 + uint64_be(sha256(network_passphrase)[0..8])` | Stellar's network ID is `sha256(passphrase)`; the `2^64` offset can never collide with an EVM chain ID |
| `asset_id(USDC)` | `1` | one asset per pool; a registry entry rather than a hash, so it is readable in events |

Stellar testnet: passphrase `Test SDF Network ; September 2015`; the value is in the vectors file.

The contract supplies all three as public inputs from its configuration: its own `chain_id`, the single remote `chain_id` it is paired with, and its `asset_id`.

**Addresses never become field elements.** Bridge recipients are SPP note public keys (already field elements), and addresses only enter the external-data hashes and attestations as bytes.

### B3. Bridge message `C`

```
h1 = P3(amount, asset_id, src_chain; 0x07)
h2 = P3(h1, dst_chain, recipient_pk; 0x07)
C  = P3(h2, claim_secret, deadline_bucket; 0x07)
```

- **Chained `P3` with the tag last** is SPP's own construction for long inputs (its GVK `r` derivation), so the circuits reuse SPP's `Poseidon2(3)` template unchanged.
- **`claim_secret`** is a uniformly random field element chosen by the sender. It makes `C` hiding, since `amount` and `recipient_pk` are low-entropy.
- **`recipient_pk`** is the recipient's SPP note public key on the destination chain.
- **`C` is a leaf of the source pool's outbox tree** (B6). A pool refuses a `C` it has already seen.

### B4. Claim nullifier

```
claim_nullifier = P2(claim_secret, 0; 0x08)
```

- Only `claim_secret` goes in, never `C`, so an observer on the destination chain can't link a claim to its `C` on the source chain.
- The `0` slot mirrors SPP's `pk = P2(sk, 0; 0x03)` and leaves room for a future second input.

### B5. Deadline bucket

```
deadline_bucket = floor(deadline_unix_seconds / 3600)        // hours since 1970
```

- Hour granularity reveals little about when a message was sent. Both chains read Unix seconds (`block.timestamp`, the Soroban ledger timestamp).
- `bridge_out` accepts `now_hour + 2 ≤ deadline_bucket ≤ now_hour + 48`. That gives the root poster and the recipient at least an hour, and keeps refunds within two days.
- `bridge_in` requires `now < deadline_bucket × 3600`.
- `refund` and `finalize` require `now ≥ deadline_bucket × 3600 + 3600`. The one-hour grace stops a claim that lands near the deadline (or across clock skew) from also being refunded.

### B6. Outbox tree

- **Same tree as the note tree:** SPP's Merkle tree with history, depth 20, `compress` nodes, "XLM" empty leaf.
- **Each `bridge_out` inserts the pair `(C, 0)`,** so `C` sits at an even index. This reuses SPP's two-leaf insertion unchanged on both chains. A `0` leaf can't be claimed, because that would need a Poseidon2 preimage of 0.
- Remote roots are posted by the root poster and kept forever (no eviction). Every posted root is from a trusted poster, and old messages must stay claimable until their deadline.

### B7. Refund note

- **`refund_commitment = P3(amount × scale_src, refund_pk, refund_blinding; 0x01)`**: an ordinary SPP note commitment on the source chain. `refund_pk` is any key the sender chooses, normally their own.
- `bridge_out` proves the refund note is worth exactly the bridged value, and stores `refund_commitment` with `C`.
- `refund` inserts the pair `(refund_commitment, 0)` into the source note tree, so the sender can spend it with a normal `transact`.
- The refund note is GVK-encrypted inside `bridge_out`, so the admin sees it too.

### B8. Circuits

Both circuits are built from SPP's templates: transaction core (keypair, signature, nullifier, Merkle proof), `Poseidon2`, and the Global View Key encryption with its low-order guard. In each one, every output amount is range-checked to 248 bits, `amount` to 64 bits, and `scale` to `{1, 10}`.

**`bridge_out`.** Spends 2 notes and creates 2 change notes, a refund note and `C`.
- **Private:** input notes (amount, blinding, sk, path, path indices), change notes (amount, pk, blinding), `amount`, `recipient_pk`, `claim_secret`, `refund_pk`, `refund_blinding`, GVK salts.
- **Constraints:**
  - SPP's input checks: each input is in the tree under `root` unless its amount is 0, its nullifier is correct, and the two nullifiers differ.
  - Value balance: `in0 + in1 = out0 + out1 + amount × scale`.
  - `changeCommitment[k]` are well formed.
  - `C` and `refundCommitment` are as in B3 and B7, with the refund amount equal to `amount × scale`.
  - **Six GVK ciphertexts:** in0, in1, out0, out1 and the refund note, as notes, plus `C`'s secrets encrypted as the note `(pk = recipient_pk, amount = amount, blinding = claim_secret)`. Indexes are 0–5 in that order.
- **Public signals, in order:** the 6 ciphertexts field-major (30), then `D[2], nonce, root, extDataHash, inputNullifier[2], changeCommitment[2], bridgeMessage, refundCommitment, scale, assetId, srcChain, dstChain, deadlineBucket` (16). Total: 46.

**`bridge_in`.** Claims `C` and creates 2 notes for its recipient.
- **Private:** all fields of `C`, the outbox path and path indices, the output notes' blindings, the split `out0, out1`, GVK salts.
- **Constraints:**
  - `C` is computed from its fields (B3) and is in the remote outbox tree under `remoteRoot`.
  - `claimNullifier = P2(claim_secret, 0; 0x08)`.
  - Both new notes are owned by `recipient_pk`, and `out0 + out1 = amount × scale`.
  - Two GVK ciphertexts, for out0 (idx 0) and out1 (idx 1).
- **Public signals, in order:** 2 ciphertexts field-major (10), then `D[2], nonce, remoteRoot, extDataHash, claimNullifier, outputCommitment[2], scale, assetId, srcChain, dstChain, deadlineBucket` (14). Total: 24.

**How the admin links a bridge.** The admin decrypts `C`'s GVK ciphertext on the source chain, which gives `amount`, `recipient_pk` and `claim_secret`. From those it computes `claim_nullifier` and finds the matching claim on the destination chain.

### B9. Contract-supplied public inputs

For every function, the contract fills in:
- `D` from storage;
- `nonce = extDataHash`, recomputed by the contract;
- `scale`, `assetId` and both chain IDs from its configuration.

The caller supplies only the roots, nullifiers, commitments, `C`, `refundCommitment`, `deadlineBucket` and the ciphertexts. All of these are checked `< r`, and the roots and deadline are checked against chain state.

### B10. Bridge delivery payload (off-chain)

- The sender encrypts `amount (32 BE) ‖ claim_secret (32 BE) ‖ deadline_bucket (8 BE)`, 72 bytes, to the recipient's X25519 key with SPP's note-delivery scheme (A, "Note delivery"). The result goes in `encryptedBridgeMessage`.
- The recipient tries to decrypt every `BridgeOut` event, then rebuilds `C` from these fields plus its own `recipient_pk` and the chain IDs.
- Change and refund notes use SPP's ordinary 48-byte note plaintext.

### B11. External-data hashes

All are reduced `mod r`, and the result is used as both `extDataHash` and `nonce`. Every hash binds the pool and token from contract state, so a proof can't be replayed on another pool.

**Ethereum** (`abi.encode`, `keccak256`, then `mod r`):

| Function | Encoded values |
| --- | --- |
| `transact` | `block.chainid, pool, token, recipient, extAmount, encryptedOutput0, encryptedOutput1` |
| `bridgeOut` | `"zkross.bridge_out.v1", block.chainid, pool, token, encryptedOutput0, encryptedOutput1, encryptedRefund, encryptedBridgeMessage` |
| `bridgeIn` | `"zkross.bridge_in.v1", block.chainid, pool, token, encryptedOutput0, encryptedOutput1` |

- `block.chainid` is bound in because the same pool address can exist on several EVM chains. SPP's Stellar pool addresses are already unique per network.
- The bridge hashes start with a string tag, so a `transact` ext hash can never equal a bridge one.

**Stellar:** SPP's scheme, `keccak256(XDR(ScMap sorted by key)) mod r`.

| Function | Map keys |
| --- | --- |
| `transact` | unchanged SPP |
| `bridge_out` | `{encrypted_bridge_message, encrypted_output0, encrypted_output1, encrypted_refund, kind: Symbol("bridge_out"), pool, token}` |
| `bridge_in` | `{encrypted_output0, encrypted_output1, kind: Symbol("bridge_in"), pool, token}` |

### B12. Refund attester and attestations

- **The attester is one secp256k1 key**, which both chains can check: `ecrecover` on Ethereum, `secp256k1_recover` on Soroban. The pool stores the key's 20-byte Ethereum address.
- **The attester needs the admin's GVK private key**, because only `claim_secret` reveals the claim nullifier to look for on the destination chain. This is an accepted testnet trust assumption.

The message and its digest:

```
message = "ZKROSS-ATTEST-v1" (16 bytes ASCII)
        ‖ src_chain        (32 bytes BE)
        ‖ source pool id   (32 bytes: Ethereum address left-padded with zeros, or Stellar contract ID)
        ‖ C                (32 bytes BE)
        ‖ status           (1 byte: 0x01 = not claimed, refund; 0x02 = claimed, finalize)
digest  = keccak256(message)
```

- **Signature:** 65 bytes `r ‖ s ‖ v` with `v ∈ {27, 28}`. `s` must be in the lower half of the curve order on both chains, so a signature can't be malleated into a second valid one.
- **`finalize(C, sig)`** with status `0x02` marks a claimed `C` settled. Its value stays in the pool as liquidity.
- **`refund(C, sig)`** with status `0x01` marks it refunded and inserts the refund note.
- Both require the grace period from B5. A `C` can be settled only once.

### B13. Liquidity

- `addLiquidity(amount)` / `add_liquidity(amount)`: the admin transfers tokens into the pool as unowned balance and an event is emitted.
- The pool keeps no per-chain ledger. Solvency is the token balance; the admin view compares decrypted totals.
- A claim that can't be paid out fails at withdrawal time, when the token transfer fails, and loses nothing.
